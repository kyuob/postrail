# FAQ와 문제 해결

[설치](installation.md) · [로그인](login.md) · [지원표](support.md) · [공통 전송](publish.md)

## 설치했는데 postrail 명령이 없어요

소스를 빌드한 것만으로 전역 명령이 생기지는 않는다. 소스에서는 `node /절대경로/postrail/dist/cli.js --help`를 사용한다. tarball을 전역 설치했다면 `bun pm bin -g`의 경로가 PATH에 있는지 확인한다. 설치된 Node.js도 `node --version`으로 확인한다.

## Chrome 앱이 왜 두 개처럼 보여요

Postrail은 평소 Chrome과 분리된 전용 프로필을 사용한다. 같은 Google 계정이라도 이 프로필에서 직접 로그인해야 한다. 평소 Chrome 프로필을 복사하거나 기존 쿠키를 추출해 해결하지 않는다. 현재 수동 Chrome 인증은 macOS만 지원한다.

## 로그인했는데 명령이 계속 기다려요

로그인에 사용한 전용 Chrome 앱에서 **Chrome → Google Chrome 종료(⌘Q)**를 실행한다. 창만 닫으면 백그라운드 프로세스가 남는다. 종료 확인창도 직접 확인한다. 평소 Chrome을 종료할 필요는 없다. 현재 로그인 대기는 시간 제한 없이 유지되며, 종료 후 계정 확인을 시작한다.

## 카카오 로그인은 됐는데 TISTORY_LOGIN_REQUIRED가 나와요

티스토리로 돌아와 **본인 블로그의 `/manage` 관리 화면**까지 진입해야 한다. 카카오 화면만 확인한 상태와 구분한다. 관리 화면 확인 후 전용 Chrome을 완전히 종료한다. 최신 Postrail은 정상 세션 복원을 사용한다. 그 상태에서도 실패하면 반복 로그인하지 말고 오류 코드·버전·관리 화면 진입 여부만 기록해 제보한다. 세션 값이나 전체 편집기 HTML은 보내지 않는다.

## Google이 브라우저가 안전하지 않다고 해요

이전 자동화 로그인 창에서 발생했던 증상이다. 현재 Velog/Tistory 로그인은 자동화 제어를 연결하지 않은 일반 Chrome을 사용한다. 최신 버전인지 확인한다. 계속 차단되면 제공자의 안내와 계정 정책을 확인한다. stealth 플래그·보안 설정 해제·쿠키 추출로 차단을 피하지 않는다. Blogger의 OAuth 동의 차단은 별도 문제이므로 [Blogger 로그인](login.md)을 확인한다.

## Velog 이메일 인증 링크가 404예요

실제 이메일 인증 교환에서 관찰한 오류지만, 404만으로 원인을 단정하지 않는다. 새 링크인지, 다른 창에서 사용했는지, 요청한 계정이 맞는지 구분한다. 링크를 이슈나 채팅에 붙이지 않는다. 이미 연결된 Google/GitHub 로그인은 별도 경로로 시도할 수 있다. 같은 실패가 반복되면 멈추고 링크를 제외한 증상만 제보한다.

## 계정이나 블로그가 다르다고 나와요

Velog는 표시 이름이 아닌 URL의 사용자명, Tistory는 canonical 서브도메인과 숫자 blogId, Blogger는 로컬 별칭과 ADMIN blogId를 확인한다. 다른 계정 세션으로 기존 글을 수정하지 않도록 중단하는 동작이다. 숫자 ID를 추측하거나 다른 사용자 ID를 넣지 않는다.

## 네 플랫폼을 전부 비공개로 보내고 싶어요

현재 모든 플랫폼에 공통으로 쓸 수 있는 비공개 상태는 없다. Tistory는 draft 슬롯을 지원하지 않고 Blogger는 private를 지원하지 않는다. 공개로 바꾸어 해결하지 않는다. `draft`는 Velog/Blogger 같은 조합, `private`는 Velog/Tistory 같은 조합으로 나누고 원고·대상을 각각 검토한다. KeyFlow의 상태 계약은 기존 가이드를 따른다.

## dry-run이 성공하면 실제 전송도 성공하나요

아니다. 파일·메타데이터·공개 상태·대상 설정만 검사하며 로그인·원격 권한·서버 가용성은 확인하지 않는다. 공통 `publish --dry-run`은 공식 KeyFlow CLI도 실행하지 않는다. 개별 `keyflow check`와 다른 동작이다.

## 일부 플랫폼만 성공했어요

JSON의 플랫폼별 결과와 각 플랫폼 `status`를 확인한다. 성공 결과는 보존하며 롤백하지 않는다. 해결된 실패 대상만 `--to`로 골라 재실행한다. `unknown`·`pending`이나 원격 충돌이 남으면 먼저 원격 결과를 확인해야 한다. 공통 명령은 자동 재시도·재로그인·다른 API 형식 전환을 하지 않는다.

아직 배포하지 않은 안정화 변경에서는 실패 결과에 `localStatus`, 선택적 `postId`, `nextAction` 안내를 추가한다. 이는 로컬 이력의 스냅샷이며 현재 전송의 원격 성공 판정이 아니다. ID가 있거나 로컬 상태가 `succeeded`여도 현재 결과의 `failed`는 그대로다. `nextAction`은 읽기 전용 확인을 위한 안내이며 새 복구 명령이 아니다. 배포된 v0.1.0에는 이 필드가 없을 수 있으므로 기존 `status`와 서비스 관리 화면도 함께 확인한다.

## unknown·pending·잠금 오류를 지우면 되나요

무작정 지우면 중복 글을 만들 수 있다. 실행 중인 프로세스가 있는지 먼저 확인하고 저장된 ID로 `get` 또는 서비스 관리 화면에서 결과를 확인한다. `get`이 성공해도 자동으로 unknown을 성공으로 승격하지는 않는다. 미배포 소스의 Velog 어댑터는 [읽기 전용 inspect와 명시적 로컬 reconcile](velog.md)을 제공한다. 원문·본문·이미지·공개 상태가 일치하고 검토 지문이 유효해야 하며, 태그 차이는 별도 승인해야 한다. 원격 글은 다시 쓰지 않는다. 공개된 v0.1.0과 다른 플랫폼에는 이 명령이 없으므로 기존 수동 확인을 유지한다. 이슈에는 토큰·본문·상태 파일 전체를 보내지 않는다.

공통 잠금은 프로젝트의 `.postrail/publish/`, 각 어댑터 상태는 `.postrail/<platform>/`에 있다. 중단된 실행의 잠금도 자동 삭제하지 않는다. 활동 중인 실행이 없고 모든 영향받은 결과를 확인한 경우에만 수동 정리를 검토한다.

## 원격 글을 지웠는데 다시 안 만들어져요

저장된 원격 ID가 없어졌다고 자동으로 새 글을 만들지 않는다. 실제 Velog 테스트에서도 사용자가 삭제한 초안의 부재를 별도로 확인했다. 같은 원고를 새 글로 만들려면 새로운 게시 의도와 ID를 명시적으로 검토해야 한다. 기존 이력을 지워 중복 방지 규칙을 피하지 않는다.

## 웹에서 직접 고친 내용은 보존되나요

Velog/Tistory/Blogger는 저장 시점 지문과 달라지면 충돌로 멈춘다. **KeyFlow는 원격 수동 수정 충돌 검출이 없으며 업데이트가 덮어쓸 수 있다.** KeyFlow를 수정할 때는 원격 내용을 직접 확인한다. 공통 명령이 이 차이를 없애지는 않는다.

이 검사는 읽기와 쓰기 사이의 동시 편집을 원자적으로 막는 기능은 아니다. 특히 Velog/Tistory에서 사전 조회 뒤 웹 편집이 발생하면 이후 쓰기와 겹칠 수 있다. 전송 중에는 다른 화면이나 프로세스에서 같은 글을 수정하지 않는다. 로컬 잠금은 다른 브라우저의 편집을 잠그지 않는다.

## Blogger 이미지·비공개 글은 왜 안 되나요

현재 Blogger 어댑터는 로컬 이미지 업로드와 개별 private 게시글을 구현하지 않았다. 공개 접근 가능한 원격 이미지 URL과 draft/public 상태를 사용한다. draft를 private 지원으로 표현하지 않으며 임의 이미지 호스팅도 하지 않는다. 원격 이미지의 장기 표시·재호스팅은 미검증이다.

## 재설치 후 새 글이 생겼어요

원격 글 ID와 콘텐츠 해시는 실행한 프로젝트의 `.postrail/`에 있다. 다른 작업 폴더에서 실행하거나 이 디렉터리를 잃으면 기존 글과 연결하지 못할 수 있다. 업데이트·이동 전에 원고와 상태를 함께 보존한다. 사용자 홈의 로그인 세션만 남아 있어도 전송 이력을 대신하지 않는다.

## 안전하게 버그를 제보하려면

Postrail 버전, OS, Node/Bun 버전, 플랫폼, 고정된 오류 코드, 재현 순서와 기대 동작을 제공한다. 새 가짜 원고와 비밀 없는 대상 예제로 재현한다. 인증 링크·쿠키·Authorization 헤더·OAuth JSON·서명 이미지 URL·개인 원고·전체 로그·스크린샷의 개인정보는 제거한다. 보안 문제는 [보안 정책](../SECURITY.md)을 따른다.
